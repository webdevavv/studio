# Чат-бриф на главной

Раздел: `/#brief`, ссылка «Бриф» в шапке. Существующая короткая форма телефона остаётся доступна отдельно.

## Сценарий

Вместо 47 вопросов используются 7–10 коротких шагов с группами быстрых ответов:

1. Готовый макет, индивидуальный сайт или помощь с выбором.
2. Компания, сфера, предложение и география.
3. Для макета — выбор из актуального каталога. Для индивидуального сайта — цель и формат.
4. Только для индивидуального проекта — разделы и функции; для каталога дополнительно объём и фильтры, для магазина — покупка, оплата, доставка.
5. Визуальные предпочтения только при индивидуальной разработке.
6. Готовность материалов и необязательная ссылка на папку или соцсети. Загрузка файлов пока не реализована: клиент передаёт ссылку или материалы позднее.
7. Технические пожелания, сроки и бюджет из центральных тарифов.
8. Контакты и проверка брифа.

Каждое поле можно оставить пустым. «Пропустить шаг» очищает поля текущего шага, «Продолжить» сохраняет заполненное. «Сразу к контактам» сокращает сценарий. «Сохранить и закончить» открывает предварительный результат с возможностью скачать TXT даже без телефона. Название компании также допускает пропуск по требованию не блокировать клиента; оно попадает в список уточнений.

История позволяет вернуться к ответам. При смене сценария скрытые нерелевантные поля не входят в итоговую заявку. География, дата запуска и контакт в мессенджере раскрываются условно. Черновик живёт только в памяти вкладки; данные не отправляются до отдельного действия и не сохраняются в localStorage.

Tab / Shift+Tab перемещают фокус, стрелки выбирают радиоварианты, Space переключает флажки. Enter в однострочном поле продолжает, в многострочном — новая строка. Ctrl+Enter / Cmd+Enter продолжают шаг. После перехода фокус попадает на вопрос, а прокрутка происходит только при необходимости. Анимация ответа длится 220 мс; reduced-motion её отключает.

## Результат и рекомендации

Описание содержит сведения клиента, выбранный формат, предварительную структуру, основные и дополнительные функции, готовность материалов, бюджет, сроки и вопросы для уточнения. Пропуски явно помечены. Сложные функции и интернет-магазин направляются на индивидуальную оценку без обещаний фиксированных сроков и цены.

**Это правила на основе ответов, не подключённая нейросеть.** Формулировки отделяют предложение структуры от фактов клиента. Для следующего этапа подключения модели передавайте `cleanAnswers(answers)` как факты, `summary(answers)` как исходный черновик. Выход модели должен отдельно содержать рекомендации, объяснения и неизвестные данные. Не передавайте контакты модели без необходимости и не давайте ей полномочия отправлять или изменять задачи. Провайдер, модель и ключ ещё не выбраны.

## YouGile API

Проверено по официальной [документации REST API v2](https://yougile.com/api/) и её `swagger-ui-init.js` 25 октября 2026 года. Для облака:

```http
POST https://yougile.com/api-v2/tasks
Content-Type: application/json
Authorization: Bearer <API_KEY>
```

```json
{
  "title": "Бриф: Название компании · ID заявки",
  "columnId": "UUID колонки новых заявок",
  "description": "<p>Описание проекта и ответы клиента</p>",
  "assigned": ["UUID менеджера"],
  "completed": false,
  "archived": false
}
```

`assigned` необязателен. `title`, `columnId`, `description` и `assigned` сверены со схемой `CreateTaskDto`. Текст клиента экранируется перед включением в HTML описания. Особенности отображения описания нужно подтвердить одной тестовой карточкой в вашем экземпляре при подключении. Успех интерфейс показывает только при успешном ответе API с ID задачи.

Публичный клиент обращается к собственному `POST /api/brief` с `{ id, answers, consent }`. Сервер проверяет источник, размер запроса, разрешённые поля, телефон и согласие, сам формирует карточку. Название колонки, менеджер, ID заявки, время создания, источник `главная /#brief`, статус согласия и следующее действие включены в заявку. Статус «Новая» задаётся выбранной колонкой. Пользовательские стикеры CRM можно подключить позже, когда будут известны их ID. Реальные статусы, комментарии и последующие действия менеджера ведутся в YouGile.

## Как подключить позже

Скопируйте `.env.example` в `.env.local` или задайте переменные в настройках сервера:

```dotenv
BRIEF_ENABLED=true
YOUGILE_API_URL=https://yougile.com/api-v2
YOUGILE_API_KEY=ваш_ключ
YOUGILE_COLUMN_ID=uuid_колонки
YOUGILE_ASSIGNED_ID=uuid_менеджера
BRIEF_POLICY_URL=https://ваш-сайт.ru/privacy
```

Для собственного сервера укажите его HTTPS-адрес с `/api-v2`. Понадобятся **адрес API, ключ и ID колонки**, а не только ссылка. Ключу нужны права создавать задачи в этой колонке. Список колонок доступен через `GET /api-v2/columns`, пользователей — через соответствующий раздел API. Не помещайте ключ в `NEXT_PUBLIC_*`, клиентский код, Git или URL.

Нужна действующая опубликованная политика с реальными данными оператора; ссылка пока не предоставлена. После подключения появится отдельный непредустановленный флажок согласия и кнопка отправки. Пока конфигурации нет, доступно только локальное сохранение, и данные не уходят в YouGile. Главная статически собирается: после изменения этих переменных выполните сборку и перезапустите сервер, чтобы обновились и интерфейс, и обработчик.

В reverse proxy должен корректно передаваться публичный host: сервер сверяет Origin с адресом запроса. При подключении проверьте тестовую заявку с телефона, текст описания, права ключа, доступность политики и назначение менеджера.

## Доставка и эксплуатация

Есть защита от двойного клика и повторного ID заявки в одном процессе (30 минут), ограничение попыток для номера (3 за 10 минут), лимит 40 КБ и таймаут YouGile 15 секунд. Персональные данные не пишутся в логи. На время дедупликации данные и номер находятся в оперативной памяти сервера.

При таймауте результат может быть неизвестен: повторная автоматическая отправка не выполняется, клиенту предлагается сохранить бриф и проверить получение. Это исключает ложное сообщение об успешной отправке, но не является гарантированной очередью доставки.

Перед запуском на нескольких экземплярах/serverless замените Map на общее хранилище с уникальным ID заявки, статусами доставки и TTL. Для публичного приёма настройте ограничение запросов на reverse proxy/хостинге: лимит только по телефону не защищает от перебора разных номеров. Долговечная очередь и общая дедупликация — отдельный этап подключения, без них защита сбрасывается при перезапуске.

## Проверки и дизайн

Использован taste-skill: Framed sheet, seed 1975747109. Сохранены Golos Text, небесные поверхности и оранжевая основная кнопка. Вопрос экрана: «Что нужно узнать о следующем решении клиента?». Полоса прогресса, быстрые ответы и история превращаются в описание проекта. Палитра узлов графа из предложенного builder не применяется: пользователь заполняет диалог, а не редактирует схему.

Первый просмотр: края панели согласованы, контролы имеют высоту от 44 px, мобильные варианты переносятся без горизонтального скролла. Визуальные состояния: старт 320/390/768/1440 px, бизнес и результат 390 px. Цвет обозначает выбранный ответ и основное действие. Счётчик шагов вычисляется из активной ветки, пропущенные ответы отмечаются как неизвестные. На мобильном история находится после активного вопроса. Небольшая анимация появления следующего вопроса добавлена по прямому пожеланию пользователя, без имитации долгого набора текста.

Тесты: `npx playwright test tests/brief.spec.ts`. Включают ветвление, очистку скрытых полей, телефон, клавиатуру, скачивание, узкие экраны, reduced-motion, экранирование, серверную валидацию, дедупликацию и неопределённый результат отправки. YouGile в тестах замокан: реальные заявки не создавались. Скриншоты: `node scripts/check-brief-ui.mjs` при запущенном production-сервере на порту 3005 (или `TEST_BASE_URL`).

Финальная проверка: production build и TypeScript прошли; полный набор Playwright — 17 успешных проверок. Inspector для статической копии реально отрисованного интерфейса: 0 FAIL, 1 WARN. Исключение `font-not-dealt` сохраняет кириллический Golos Text существующего сайта; предупреждение `hero-void` относится к пустой области ниже короткого изолированного интерфейса в тестовом окне, а не к отступу внутри главной. Скриншоты самого сайта и отдельные состояния просмотрены на всех указанных ширинах. Рекомендация после получения реального контента: проверить длительность прохождения на нескольких клиентах; 2–4 минуты — ориентир, не измеренная пользовательская метрика.
